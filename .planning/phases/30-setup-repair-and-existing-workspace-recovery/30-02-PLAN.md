# Plan 30-02: Derive Repair Steps from Durable Setup State and Doctor

## Why

Repair should not ask the operator to guess whether they need gateway, channel, model, or control-plane setup. The product already knows a lot about failed bootstrap surfaces and first-start blockers.

## Implementation

1. Build a repair-plan helper that maps unfinished setup steps, failed bootstrap outcomes, and doctor diagnostics back to onboarding steps.
2. Reuse the durable setup-state contract to mark the selected repair steps as active.
3. Add focused unit tests for repair-plan derivation and setup-state repair preparation.

## Verification

- `cargo test -p openrustclaw-cli onboard -- --nocapture`
