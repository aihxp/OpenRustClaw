# Cross-AI Plan Review — Phase 61

## Gemini Review

Here is the cross-AI review for Plan 61-01 based on the provided project context and requirements.

### 1. Summary

The plan accurately translates the phase goal and context into a targeted refactoring effort. By focusing specifically on the `self_hosted_product_mode_summary`, it successfully scopes down the overarching goal of extracting inspection business logic from `inspect.rs` into `openrustclaw-app`. The plan respects the established architectural constraints by keeping the storage and state-loading mechanisms in the CLI layer while moving only the composition and transition-target calculations into the application layer. 

### 2. Strengths

*   **Strict Scope Adherence:** The plan strictly follows the context's constraint to avoid broadening scope into control-route extraction or moving the persisted storage out of the CLI module.
*   **Clear Verification Strategy:** The testing strategy explicitly targets both the new unit (the app-level service) and the existing consumers (the CLI-level summary and dashboard panels), ensuring the existing UI/runtime contract remains truthful.
*   **Architectural Alignment:** It accurately identifies `inspect.rs` as needing to become a "thin adapter," which is the exact architectural shift OpenRustClaw has been executing to separate CLI concerns from core application business logic.

### 3. Concerns

*   **MEDIUM: High-Level Abstractions without Signatures:** The plan describes adding a "service boundary" but does not define the structural boundaries (e.g., input data types, expected return structs, or trait definitions). This leaves room for the developer to accidentally couple CLI-specific types to the `openrustclaw-app` layer during implementation.
*   **LOW: Missing Error Handling Specifications:** The plan does not mention how error cases (e.g., malformed state, missing data) should be handled or mapped between the new app service and the CLI adapter. 
*   **LOW: Dependency on `self_hosted.rs` isn't Explicit:** The context notes that persisted state lives in `self_hosted.rs`, but the plan doesn't mention how `inspect.rs` will coordinate with `self_hosted.rs` to gather the necessary data to feed the new service.

### 4. Suggestions

*   **Define the Interface:** Specify the exact data structures the new `openrustclaw-app` service will accept and return. For example, explicitly state that `inspect.rs` will pass a clean, CLI-agnostic struct to something like `ProductModeSummaryService::compose(...) -> ProductModeReport`.
*   **Explicit Error Mapping:** Add a brief step detailing how errors generated by the new application service will be propagated and displayed by the `inspect.rs` adapter.
*   **Test Edge Cases:** Update the Verification section to explicitly mention testing edge cases, such as incomplete or corrupted self-hosted product-mode state, to ensure the new composition service handles bad data gracefully.

### 5. Risk Assessment

**LOW**

**Justification:** The risk is low because this is a pure refactoring task with a strictly bounded scope. It does not introduce new features, alter data storage mechanisms, or modify the final output format. As long as the existing regression tests for the dashboard and product-mode panels pass (as specified in the verification steps), the chance of negatively impacting the user experience or system stability is minimal.
