# Cross-AI Plan Review — Phase 84

## Gemini Review

Here is the cross-AI plan review for Phase 84, Plan 84-01.

### 1. Summary

Plan 84-01 provides a high-level, structurally sound approach to migrating the read-heavy status route family (runtime, voice, talk, mobile) from the HTTP delivery layer (`start.rs`) to the application layer (`openrustclaw-app`). By isolating the HTTP adapter concerns from the domain logic of report composition and limit defaulting, the plan successfully targets the phase's core objective. However, the plan is extremely brief and lacks technical specifics regarding error boundary translation, dependency injection for the new service, and a concrete list of the affected routes, which could lead to missed endpoints or misaligned error codes during implementation.

### 2. Strengths

* **Clear Architectural Boundaries:** The plan correctly identifies the exact boundary line—`start.rs` remains responsible for HTTP semantics (parsing/wiring) while `openrustclaw-app` takes over domain logic (orchestration/limits).
* **Scope Discipline:** It strictly adheres to the constraint of touching only read-heavy status surfaces, avoiding scope creep into mutation or setup flows.
* **Targeted Verification:** The included verification steps explicitly target both the underlying application logic and the CLI/operator surface, ensuring the public contract remains truthful.

### 3. Concerns

* **[MEDIUM] Opaque Error Handling Translation:** The plan does not specify how domain errors generated by the new `openrustclaw-app` service will be mapped to HTTP status codes in `start.rs`. Without an explicit error mapping strategy, the API contract could inadvertently change (e.g., returning 500s instead of 404s or 400s).
* **[MEDIUM] Missing Dependency Injection Details:** There is no mention of how the new status service will be instantiated, lifecycle-managed, and injected into the router state within `start.rs` (e.g., via Axum/Actix app state).
* **[LOW] Undefined Route Inventory:** The plan relies on a general description rather than an explicit checklist of endpoints (e.g., voice metrics, talk sessions, mobile node summaries). This creates a minor risk of orphaned inline handlers being left behind in `start.rs`.
* **[LOW] Unspecified Limit Defaulting:** While "limit normalization" is mentioned, the plan lacks details on what the default pagination or sizing limits actually are, which is critical for consistent read-heavy report shaping.

### 4. Suggestions

* **List Affected Routes:** Add an explicit sub-list under Step 2 enumerating the exact endpoints being migrated (e.g., `/api/v1/status/runtime`, `/api/v1/voice/sessions`, etc.) to serve as a completion checklist.
* **Define the Service Trait/Interface:** Briefly outline the public methods the new service will expose to `start.rs` (e.g., `get_mobile_node_summary(query: &Query) -> Result<Summary, AppError>`).
* **Specify Error Mapping:** Explicitly state that `start.rs` will implement an adapter mapping for the new service's `Result` types to ensure the existing HTTP error code contract is strictly preserved.
* **Detail State Injection:** Add a brief note on how the new service will be integrated into the existing application state or dependency injection container used by `start.rs`.

### 5. Risk Assessment

**Risk Level: LOW**

**Justification:** The architectural risk is very low because the operation is a pure refactor of read-only data paths, meaning there is virtually no risk of data corruption or disrupted state mutations. The primary risks are execution-related (missing an endpoint or altering an HTTP status code). As long as the existing test suite has adequate coverage for the HTTP responses of these status endpoints, any regressions introduced by the lack of detail in the plan will be caught immediately by the compiler or the integration tests.
